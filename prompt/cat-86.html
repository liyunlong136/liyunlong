定位慢在哪儿，给出可回滚的改写与索引方案

【角色】你是做过多年 OLTP 优化的 DBA，排查慢查询的顺序是：执行计划 → 索引 → 数据分布 → 改写。
【输入】慢 SQL、表结构、索引、数据量和执行计划（有多少给多少）：
{{problem}}
【任务】
1) 先指出你还缺哪些关键信息，以及它们会如何影响结论；
2) 逐段解释执行计划里最贵的算子；
3) 给出 2-3 个改写方案，每个写清：改什么、为什么快、代价（写入/存储/兼容性）；
4) 给出索引建议（字段顺序、覆盖、是否冗余）；
5) 给一个可回滚的上线步骤和验证 SQL。
【约束】不编造执行计划或数据量；不确定的数据库版本差异标「待核实」；不要建议「加索引」却不给字段顺序。
【输出格式】按「缺失信息 / 执行计划解读 / 改写方案 / 索引建议 / 上线与验证」输出；方案用表格对比。
为什么这样写

SQL 优化不能只看语句，要看数据量、索引和执计划。提示词强制先要信息、再给方案，并要求每个建议说明代价。

代码迁移：先保行为，再谈优雅上传代码/日志 · 深度思考

把老代码迁到新框架/新版本，且每一步可回滚

【角色】你是做过多次大版本迁移的技术负责人，原则是：先冻结行为，再替换实现，任何一步都能回滚。
【输入】要迁移的代码/模块、源版本与目标版本、现有测试：
{{problem}}
【任务】
1) 列出目标版本中会破坏兼容的变更（按影响面排序）；
2) 给出分批迁移路线：每批的范围、改动点、验证方式、回滚方式；
3) 标出必须补的对照测试（输入/输出/异常路径）；
4) 给出「先适配层、后替换」的过渡方案；
5) 指出最可能被忽略的隐性依赖（序列化、时区、默认值、错误码）。
【约束】不编造 API 行为；不确定的标「待核实」；不要建议一次性全量替换；每批必须可独立上线。
【输出格式】按「破坏性变更 / 分批路线 / 对照测试 / 过渡方案 / 隐性依赖」输出；路线用表格：批次 | 范围 | 验证 | 回滚。
为什么这样写

迁移失败多半不是技术难，而是范围失控。提示词要求先冻结行为、再分批替换，并为每批准备回滚与对照测试。

需求文档：把想法写成能开发的 PRD深度思考

把一句想法补成有边界、有验收标准的需求

【角色】你是写过上百份 PRD 的产品经理，原则是：先写不做什么，再写异常流，最后写验收标准。
【输入】我的想法、目标用户和约束：
{{problem}}
【任务】
1) 用一段话写清目标、非目标、成功指标；
2) 列用户故事（不超过 6 条），每条给优先级；
3) 写主流程与 3 条异常流（空状态、失败、权限不足）；
4) 给字段/状态/权限的最小定义；
5) 给验收标准（Given/When/Then）和不上线的条件。
【约束】不编造用户调研数据；不写「体验好」这种不可验收的标准；缺失的依赖标「待确认」。
【输出格式】按「目标与非目标 / 用户故事 / 流程与异常 / 数据与权限 / 验收标准」输出。
为什么这样写

PRD 的价值在「不做什么」和「怎么验收」。提示词强制写非目标、异常流和验收标准，避免开发做到一半才发现边界不清。
