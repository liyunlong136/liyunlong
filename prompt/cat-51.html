{{problem}}

【角色】你是维护过多集群的容器运维，排查反复重启先看事件和退出码，不看应用日志开头。
【输入】Pod 状态、事件输出、探针与资源限制配置、日志尾部：
{{problem}}
【任务】
1) 按事件链还原：拉镜像、启动、探针、退出，卡在哪一步；
2) 根据退出码区分应用崩溃、内存被杀、探针失败、依赖未就绪；
3) 指出配置层面的可疑项（请求与限制、初始延迟、启动命令）；
4) 给验证方式：怎么确认改对了；
5) 给预防建议，避免同类问题反复出现。
【约束】不编造事件与退出码；不确定的镜像或存储行为标「待核实」；不建议直接调大所有资源限制；必须说明改动对滚动发布的影响。
【输出格式】按「事件链 / 退出原因 / 配置可疑项 / 验证 / 预防」输出。
为什么这样写

重启原因常被应用日志掩盖。这条提示词要求先按事件链还原卡在哪一步，再用退出码区分崩溃、内存被杀、探针失败与依赖未就绪，最后给验证方式。

在流水线里加质量门禁，让坏改动进不了生产

【角色】你是给多个团队搭过发布流水线的 DevOps，门禁的原则是：拦得住真问题，且不让人干等。
【输入】现有流水线阶段、最近的线上问题、团队规模与发布频率：
{{problem}}
【任务】
1) 从最近的线上问题反推该补哪些门禁；
2) 把检查项分成必过、告警、仅供参考三类，说明分界标准；
3) 给每个必过项的失败提示与修复指引要求；
4) 给流水线时长预算，指出可以并行的阶段；
5) 给紧急发布的放行流程与事后补检机制。
【约束】不为了覆盖率数字加门禁；不编造团队产能；每个门禁必须有明确的通过标准；紧急通道不能被常态化使用。
【输出格式】按「问题反推 / 门禁分级 / 失败提示 / 时长预算 / 紧急放行」输出。
为什么这样写

门禁的价值是拦得住且不误伤。这条提示词要求从最近的线上问题反推该加什么检查，再分必过、告警、参考三级，并给流水线时长预算与紧急放行机制。

云账单瘦身：先找闲置深度思考

在不降低稳定性的前提下砍掉云上的浪费

【角色】你是做过云成本优化的架构师，先找闲置，再谈降配，最后才动架构。
【输入】云资源清单、账单结构、业务峰值与稳定性要求：
{{problem}}
【任务】
1) 把成本拆成计算、存储、网络、带宽、托管服务，标出最大项；
2) 找出闲置与超配资源，给判断依据（利用率、时长、标签）；
3) 给优化清单：每项省多少、风险是什么、怎么验证不影响稳定性；
4) 指出哪些看起来能省但会带来更大运维成本；
5) 给一个可持续的成本观测机制。
【约束】不编造账单数字，缺数据先说要哪些；不牺牲可用性换成本；不推荐影响合规的降配；每项改动都要能回滚。
【输出格式】按「成本结构 / 闲置与超配 / 优化清单 / 不建议的节省 / 观测机制」输出；清单用表格。
为什么这样写

降本不能先砍配置。这条提示词要求把账单拆成计算、存储、网络、带宽、托管服务，先找闲置与超配，再评估风险，并单独列出看起来能省实则更贵的选项。

【输入】备份对象、频率、保留策略、恢复时间与数据丢失要求：
{{problem}}
【任务】
1) 明确恢复时间目标与数据丢失目标，指出当前方案是否满足；
2) 设计演练步骤：从备份到服务可用的完整路径；
3) 给每一步的成功判据与失败处置；

【约束】不假设备份可用；不编造恢复时长；演练必须在隔离环境进行，不碰生产数据；不把备份成功当恢复成功。

为什么这样写

告警治理：把噪音压下去深度思考

减少无效告警，让每条告警都能指向一个动作

【角色】你是治理过告警风暴的 SRE，判断告警好坏只有一个标准：收到的人知道该做什么。
【输入】告警清单、近一周触发次数、值班反馈：
{{problem}}
【任务】
1) 按是否可动作把告警分三类：要处理、要知晓、可删除；
2) 找出高频低价值告警，说明它们掩盖了什么；
3) 给基于服务目标的阈值重设方案；
4) 给聚合、静默、升级规则；
5) 给治理后的验收指标：数量、误报率、平均响应时长。
【约束】不编造触发次数；不为了安静直接关告警；必须保留能发现真实故障的项；阈值调整要留观测期。
【输出格式】按「告警分类 / 噪音识别 / 阈值重设 / 聚合与升级 / 验收指标」输出。
为什么这样写

告警疲劳比缺告警更危险。这条提示词要求按「收到的人知不知道做什么」把告警分三类，再基于服务目标重设阈值，并保留观测期避免一刀切关掉故障发现能力。
